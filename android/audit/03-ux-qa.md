# Phase 3 — UX / UI quality

> Heuristic + reference-anchored UX/UI audit of the Android `:app` native shell against two yardsticks: **OSRS Mobile** (the *feel* target — the official Jagex touch client this build emulates) and **RuneLite desktop** (the *feature* parity target). 48 findings, every one adversarially verified (CONFIRM / ADJUST / OVERTURN). **Severity = the verified-corrected value**, not the finder's first pass — several P1/P2s were honestly downgraded once a recovery path or already-shipped fix was found, and four findings were refuted outright (already-fixed or bad reference) and moved to §6 to credit the prior work. Stable ids are cited verbatim by the ROADMAP.
> "Measurement" tags: **inspection** = the defect is statically provable from code; **needs-device** = the *feel/notch* magnitude must come from the end-of-audit device batch (see §5).
>
> **Severity rubric (this UX audit grades by user-experience impact, NOT by bug-tracker correctness):** **P0** = crash / hang / data-loss / hard release-blocker; **P1** = a *major* UX failure that significantly impairs feel or a core flow **even when technically recoverable** — first-impression damage, status-invisibility on a core multi-second transition, or occlusion of a *sole* control; **P2** = a moderate problem with an easy workaround; **P3** = polish / consistency. Because severity tracks experience impact (not "does the app eventually recover"), several P1s here are recoverable by design — that is intentional, not inflation. Counts: **48 findings total = 44 open (P1=5, P2=12, P3=27) + 4 refuted (§6)**; the §3 master table lists exactly the 44 open ids.
>
> **OSRS-Mobile reference currency:** OSRS-Mobile behaviors cited as the *feel* yardstick reflect the official Jagex client's documented behavior as of this audit (2026-06). That client evolves, so any high-impact OSRS-Mobile reference — and especially the §6 "bad-reference" refutations — should be spot-checked against the *live* app during the device QA batch (§5) before acting on it.

## 1. TL;DR

The app is a **competent desktop-RuneLite-on-a-phone with a thin native HUD veneer**, but it does not yet *feel* like an OSRS-Mobile-class product. The headline gaps fall into four clusters:

- **First impressions are unfinished.** Cold start is a **~30 s frozen black screen** with zero progress/branding (UX-ONBOARD-01); the home-screen identity is the dev codename **"HelloShell"** with a TV banner reused as the launcher icon (UX-ONBOARD-03); the Jagex login is a bare black `LinearLayout` (UX-LOGIN-02/UX-XCUT-06).
- **Status invisibility on the long, multi-second transitions.** A routine **world hop reads as a kick** — ~8 s of raw engine login chrome with no "Hopping…" scrim (UX-DISCRETE-01); a **session lapse / autologin-exhaustion** parks on the raw desktop login form with no native "sign in again" status (UX-LOGIN-01); hop *failures* give up silently (UX-DISCRETE-07).
- **Native-vs-desktop parity debt.** The Compose **config editor drops the `@ConfigSection` grouping** the bridge already emits and iOS already consumes (UX-PLUGCFG-01); chat compose is a buried bottom-left glyph (UX-HUD-01); screenshots silently fail under 2 of 3 renderers (UX-DISCRETE-03).
- **Mobile fundamentals missing app-wide.** **No window-inset handling** on the native HUD controls, the long-press menu, or the entire Compose sheet — primary controls run under the landscape cutout / gesture bar (UX-XCUT-01/02/03); **zero accessibility semantics** anywhere (UX-XCUT-04); **no OSRS theme** on the Compose layer, so it reads as a generic dark Material settings app bolted onto the game (UX-XCUT-05).

**Verdict: a desktop port with a native veneer, not yet an OSRS-Mobile-class app.** The in-game classic-View veneers (chat/minimap/tab-grid) are genuinely well-styled and inset-correct; the seam is everything *around* the scene — onboarding, the Compose config/panel layer, the long transitions, and safe-area/a11y hygiene.

**Open defect counts (verified-corrected severity):**

| P0 | P1 | P2 | P3 | total open | refuted (§6) |
|---|---|---|---|---|---|
| **0** | **5** | **12** | **27** | **44** | **4** |

The five P1s: UX-ONBOARD-01 (black cold start), UX-LOGIN-01 (silent session-lapse login), UX-PLUGCFG-01 (config sections dropped), UX-DISCRETE-01 (world hop reads as kick), UX-XCUT-01 (primary HUD controls under the cutout).

**Does it feel like a polished OSRS-Mobile-class app or a desktop port?** → **A desktop port with a native veneer.** The biggest *feel-gaps*:

1. **Dead air on every long transition** (cold start, world hop, session re-auth) — the user repeatedly can't tell "working" from "broken/kicked."
2. **The Compose layer is a different app** — generic dark Material with no OSRS theme/typeface, dropping the section grouping and a11y that the engine-side veneers already nail.

5. **Unhappy paths dead-end** — failed hop, exhausted autologin, failed screenshot, failed Hub install all stop with a terminal string and no retry.

## 4. Detailed findings by cluster

Each finding: what's wrong · reference violated · heuristic · severity · evidence (`file:line`) · proposed fix · effort · scope · measurement. ADJUST findings carry the **corrected** severity and a note on the framing fix.

### 4.1 Onboarding & login

**UX-ONBOARD-01 — Black first-launch screen for the full ~30 s unpack+boot (P1, insp, M, android).** `setContentView(root)` paints an empty FrameLayout whose Z0 SurfaceView is black, then the jvm-boot thread runs `AssetInstaller.ensureInstalled` — a single-threaded 8 KB-buffered copy of a 198 MB tree (~30 s, see PERF-COLD-START-01) — before any frame paints. No splash theme, no ProgressBar, no copy. A frozen-black screen on first run reads as a hang/ANR. *Ref:* OSRS-Mobile shows a branded splash + progress on first run; RuneLite desktop has a SplashScreen with a progress bar (the one this build gates off via `runelite.nosplash` — a *desktop* window, not a native loading view, so the MOBILE-UX "Splash | Infeasible" row does not overturn this). *Heuristic:* visibility of system status. *Evidence:* `MainActivity.kt:673` (setContentView) `:912` (boot thread) `:2564-2565` (ensureInstalled); `AndroidManifest.xml:29` (stock theme); no `values/`/`mipmap`. *Fix:* add a windowBackground splash theme **or** a full-screen branded loading View before the boot thread, dismissed on the first engine frame; on first install, post a 0-100% from `ensureInstalled` bytes-copied. The existing `ReconnectingOverlayView` OSRS spinner can be reused.

**UX-LOGIN-01 — Permanent autologin failure drops to the raw desktop login with no native recovery (P1, dev, M, android · ADJUST).** The reconnect scrim is gated only on the CONNECTION_LOST `reconnecting` flag (`MainActivity.kt:1869-1875`; `HeadlessLogin.isReconnecting()` true only during a network-drop recovery), so a credential/token failure (expired session, INVALID creds, members bounce) lands on the login screen with **no** scrim and **no** "failed vs still trying" status — the snapshot carries no autologin-exhausted flag. *Corrected framing:* one evidence claim was wrong — a recovery route **does** exist (the "Account" tile, `MainActivity.kt:521` → LoginActivity, re-logs without deleting tokens), it's just buried in the Plugins launcher and undiscoverable in the failure state. The central status-visibility gap holds → **P1 retained**. *Ref:* OSRS-Mobile shows a native touch-sized session-expired screen; the relocated/scaled engine login is a poor touch target. *Heuristic:* visibility / error recovery. *Fix:* surface a failure-family flag through the chrome bridge (like `reconnecting`) and show a native "Session expired — sign in again" overlay that launches LoginActivity, distinct from the transient reconnect scrim.

**UX-ONBOARD-02 — POST_NOTIFICATIONS requested cold on first onCreate, no rationale, no denial handling (P2, insp, S, android).** `setupNotifications()` runs unconditionally (`MainActivity.kt:373`) and fires `requestPermissions(POST_NOTIFICATIONS)` (`:1737`) on API 33+ over the black unpack screen, with no `shouldShowRequestPermissionRationale` and no `onRequestPermissionsResult` — a denial is silently swallowed forever with no in-app re-enable path. *Nuance:* channels **are** created unconditionally before the request, so the proposed "leave channels created" is already partly satisfied; the core defect (cold blind request, no rationale, no result handler) stands. *Ref:* in-context request + rationale (OSRS-Mobile / Android guidance). *Heuristic:* user control / error prevention. *Fix:* defer to in-world, gate behind a rationale, add `onRequestPermissionsResult`, expose an "Enable notifications" deep-link in the panel.

**UX-ONBOARD-03 — Dev codename "HelloShell" + TV banner reused as launcher icon (P2, insp, S, android).** `android:label="HelloShell"` and both `android:icon`/`android:banner` = `@drawable/tv_banner`, a 320×180 brown-gradient TV tile (the drawable's own comment confirms). No `mipmap`, no adaptive icon, no `values/strings.xml`. The product's first impression reads as an unfinished dev build. *Ref:* OSRS-Mobile adaptive icon + "Old School RuneScape" label. *Heuristic:* match / aesthetic. *Evidence:* `AndroidManifest.xml:24-26`; `res/drawable/tv_banner.xml`. *Fix:* add an adaptive launcher icon (`mipmap-anydpi-v26` fg+bg), move the name to `@string/app_name`, keep the TV banner only on `android:banner`.

**UX-LOGIN-02 — Jagex login built from bare un-described widgets, no accessibility or in-flight state (P2, insp, S, android).** Raw `LinearLayout/Button/EditText/TextView` (`LoginActivity.kt:55-111`), no `contentDescription`/`labelFor`/`inputType`; the "Import login link" button is never disabled during the up-to-35 s mint (`connectTimeout=15000`+`readTimeout=20000`, `JagexLogin.kt:152-153`) — only a bottom status `TextView`, no spinner — so the long mint reads as stalled. *Nuance:* the status-during-mint half is stronger than the accessibility half (the instructional copy is largely self-describing on a once-per-token screen). *Ref:* OSRS-Mobile accessible login + disabled-button-plus-spinner in-flight state. *Heuristic:* accessibility / visibility / consistency. *Fix:* add `contentDescription`/`labelFor`/`inputType=textUri`; disable Import+Open + show an indeterminate ProgressBar during `handleRedirect`; apply the OSRS palette to the header/background.

**UX-LOGIN-03 — Clipboard-import errors give thin, non-actionable guidance (P3, insp, S, android).** No-browser → "✗ no browser available" (`:133`) with no Chrome/Play-Store guidance; bad paste (`:98`) and failed mint (`:187`) carry thin textual hints but **no inline retry button** (the "Open Jagex login" button is at `:82-85`, requiring a scroll back up); auto-import only fires on an already-correct clipboard (`:147-151`). *Ref:* the Cloudflare clipboard handoff is unavoidable (documented), so the bar is self-explanatory + one-tap-recoverable failures. *Heuristic:* error recovery. *Fix:* name Chrome + Play-Store deep-link on the no-browser path; add an inline "Open Jagex login again" beside each error; hint on a wrong-clipboard paste.

**UX-ACCOUNT-01 — RuneLite-account Custom Tab backgrounds the app and drops the game session, no warning (P3, dev, M, android · ADJUST).** Account "Log in" → `RuneLiteAccountBridge.startLogin` → `SessionManager.login` → `LinkBrowser` → Custom Tab; backgrounding drops the game to LOGIN_SCREEN in ~7 s (device-QA confirmed). The session JSON is only `{available,loggedIn,username}` — no "sync in progress" — and there is no up-front warning. *Corrected framing:* "no reconnect affordance" is **partly overturned** — FIX-9's auto-reconnect (CONNECTION_LOST-gated) + the native "Reconnecting…" overlay already surface the on-return reconnect; only the up-front notice + "Synced as <user>" confirmation are genuinely absent, and the underlying drop is an accepted P3 keepalive divergence (PERF-BATTERY-NETWORK-01/-02) → **down to P3**. *Ref:* RL OAuth never disconnects the game. *Heuristic:* visibility / error prevention. *Fix:* one-line pre-launch notice + a "sync in progress/synced" state on the row; longer-term fold into background-keepalive.

**UX-ACCOUNT-02 — Legacy login + account-sync are undiscoverable from onboarding (P3, insp, S, android · ADJUST).** The first-launch gate launches only Jagex LoginActivity (`MainActivity.kt:893-901`); the legacy username/password path has **no in-app entry** (`legacy_login.json` must be adb-pushed, `LegacyCreds.kt:26-32`). *Corrected framing:* the headline "unlabelled RuneLite-account row" is **wrong** — `PluginPanel.kt:344-346` already renders "RuneLite account" + the subtitle "Sync your profiles + installed plugins" and hides the row when the bridge is unavailable. So the only undone work is sharper wording ("not your game account") + documenting legacy as dev-only → **P3**. *Ref:* RL labels game-login vs account-sync separately. *Heuristic:* recognition / match. *Fix:* sharpen the subtitle; add an explanatory line to LoginActivity tying the two; document legacy as dev-only.

### 4.2 Play + input

**UX-PLAYINPUT-01 — No confirming haptic at long-press menu open (P2, insp, S, android).** `beginMenuPeek()` / `beginChatFilterMenu()` (`MainActivity.kt:2231-2262`) set `menuActive=true` and post the right-click but never call `vibrateTick()`; haptics fire only later on row-change (`:2389`) and drill-in (`:2361`). On a finger-occluded menu there's no signal the hold registered until movement. iOS mirrors the gap (`ViewController.m:4072-4074` only `prepare`s) — a shared OSRS-Mobile-feel gap, not an Android regression. *Ref:* OSRS-Mobile fires a distinct haptic the instant the menu opens (Android `HapticFeedbackConstants.LONG_PRESS` convention). *Heuristic:* visibility / recognition. *Fix:* one `vibrateTick()` (or a stronger ~25 ms one-shot) at the top of both `begin*Menu` paths.

**UX-PLAYINPUT-02 — Long-press uses the 500 ms system default vs iOS 400 ms (P3, dev, M, android · ADJUST).** `GestureDetector` is built with no timeout override (`MainActivity.kt:739`) → inherits 500 ms; iOS sets `minimumPressDuration=0.4` (`ViewController.m:657`). *Corrected framing:* the finding wrongly lumps in the chat-tab long-press — that path uses its own `LONG_PRESS_MS=350L` (`ChatPillView.kt:41`), already faster than iOS, so "inherits 500 ms" is false for chat. Narrower than stated, a 100 ms feel-tuning delta → **P3**. *Ref:* OSRS-Mobile snappy tap-hold; iOS 0.4 s parity. *Heuristic:* consistency / match-feel. *Fix:* a custom 400 ms `Handler.postDelayed` long-press detector (cancel on slop), matching iOS.

**UX-PLAYINPUT-03 — Tap-mode menu silently swallows the first post-release tap (P3, dev, M, android).** Tap-mode (submenu/Shift) menus: the first ACTION_UP only sets `menuTapArmed=true` and returns (`MainActivity.kt:753-761`); only the second tap acts. The arming source diverges — if the menu builds after the finger is up, `tryBuildNativeMenu` arms immediately (`:2275`) so the next tap selects; if it built while the finger was down, the release is the wasted arming event — so the user can't predict which path they got. No visual/haptic cue marks the arming. *Ref:* OSRS-Mobile persistent menus are tap-ready the instant they appear. *Heuristic:* visibility / consistency. *Fix:* arm `menuTapArmed` the moment the menu is presented regardless of finger state; make a deliberate lift-then-tap actionable; at minimum flash a highlight when tap-ready.

**UX-PLAYINPUT-04 — Failed menu build tears down silently after 1 s (P3, insp, S, android).** `tryBuildNativeMenu` polls ≤1 s; on timeout it logs "no engine menu within 1s — aborting" and `teardownMenu()` (`MainActivity.kt:2279-2282`) with no overlay/haptic ever shown. Combined with -01 (no open haptic), a long-press over empty ground is completely invisible — held 500 ms, felt nothing, saw nothing. *Ref:* OSRS-Mobile always acknowledges a long-press. *Heuristic:* visibility / error prevention. *Fix:* pair with -01's open-haptic so the press is always acknowledged; optionally shorten the 1 s abort.

**UX-PLAYINPUT-05 — Inventory/reorder item-drag begins on the first scroll, no hold gate (P3, dev, M, shared).** `onScroll` gesture-start: `inDraggablePane` → `itemDragging=true` + MOUSE_PRESSED on the first slop-crossing scroll (`MainActivity.kt:1312-1327`), no press-hold and no pickup haptic — a glancing drag over the dense grid accidentally rearranges an item. iOS mirrors the no-hold model (`ViewController.m:4708-4719`) → shared gap; FIX-4 wired the drag but added neither gate nor haptic. *Ref:* OSRS-Mobile gates rearrange behind hold-then-drag + buzzes on pickup. *Heuristic:* error prevention / match. *Fix:* require a ~150-200 ms dwell before the drag arms (early lift = a normal tap), add a `vibrateTick()` on MOUSE_PRESSED, keep the always-fire RELEASE.

**UX-PLAYINPUT-06 — Tap-feedback ring is ~1.8× the iOS/OSRS-Mobile marker (P3, dev, S, android).** `baseRadius=16dp`, `stroke=3dp` (`TapRingView.kt:24,26`) vs iOS `r0=9pt`, `lineWidth=2.5` (`ViewController.m:4019,4025`), same scale/fade/duration — Android's marker is visibly chunkier and partly occludes nearby entities right after a tap. *Ref:* OSRS-Mobile small crisp ring; iOS deliberately sized to mirror it. *Heuristic:* aesthetic / consistency. *Fix:* drop `baseRadius`→~9dp, stroke→~2.5dp; verify visibility on busy scenes.

### 4.3 HUD / chat / minimap

**UX-HUD-01 — No chat-compose affordance on the chat row; compose is a buried bottom-left ⌨ glyph (P2, insp, M, android · ADJUST).** The top chat veneer (`ChatPillView`) draws only tabs (`:209-215`); the only compose path is the ⌨ `devButton` in the bottom-left devBar (`MainActivity.kt:566-572`), spatially divorced from the chat. *Corrected framing:* the core "you cannot compose chat" is **solved** — the manual ⌨ keyboard summon (AP-0) shipped and works; what remains is co-location/discoverability, and the iOS sibling brief raises the identical open gap (tap-chat-to-raise-keyboard).
