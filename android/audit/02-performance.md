# Phase 2 — Performance & efficiency

> Audit of the Android `:app` runtime cost: cold-start unpack/warmup, frame-pacing/jank, Compose-UI over-recomposition, memory/thermal/renderer-robustness, and battery/network. 34 findings, every one adversarially verified (CONFIRM / ADJUST — no OVERTURN this batch). Corrected impact/severity from verification is used throughout; stable ids are cited verbatim by later phases + ROADMAP.
> Severity uses the verified-corrected value (several P1s were honestly downgraded once the cost was sized; two P1s held). "Measurement" tags: **inspection** = mechanism statically provable from code/on-disk bytes; **needs-device** = the magnitude (seconds, fps, MB, mA) must come from the end-of-audit device batch (§5).

## 1. TL;DR

The single biggest UX cost is the **~30 s first-launch unpack** (`AssetInstaller` copies a 198 MB tree single-threaded through an **8 KB** buffer) and its **re-fire on every jar rebuild**. The headline win is cold-start: shrink the copy work and the copy *granularity*, with no new toolchain artifact required. After cold-start, the recurring cost is **release-armed diagnostics** (gpuframedump / fpsprobe / headless.capture) doing PNG encodes + per-frame bookkeeping on the warmup critical path, and **per-frame UI-thread JSON re-parsing** that the sibling map path already short-circuits. The two genuinely material *steady-state* risks are device-confirmed **117HD thermal throttle** (no governor) and a **pinned core/GPU while backgrounded** (no visibility gate).

**Top perf wins (punchlist):**

1. **Cold-start: bump the copy buffer 8 KB → 1 MB and stop unpacking the 3 unbooted jars** (shaded 30.6 MB + gpu-smoke + hello). ~30.8 MB less copy + far fewer syscalls. *Expected: several-fold large-file throughput, plausibly **~5–10 s off** the ~30 s unpack; **−30.6 MB** filesDir.* (PERF-COLD-START-01)
2. **Cold-start: make the re-unpack incremental** (split JRE-under-BASE from jars-under-tag). A jar-only rebuild recopies ~38 MB not 198 MB. *Expected: **~30 s → a few s** on every dev redeploy / app update.* (PERF-COLD-START-06)
3. **Gate the release diagnostics behind `BuildConfig.DEBUG`** (gpuframedump / fpsprobe / headless.capture — mirror the adjacent `setStdioRedirect(BuildConfig.DEBUG)`). *Expected: removes up to **8 in-world-warmup PNG encodes** (accelerated) + up to ~26 capture PNGs + per-frame branches; measurable warmup-stutter + small steady CPU/IO/battery win, zero release diagnostic loss.* (PERF-FRAME-PACING-03/04/05, PERF-COLD-START-04)
4. **Background/visibility gate the engine + render loop** (a `g_paused` atomic from onStop drops the 60 Hz JNI poll to ~4 Hz; longer lever lowers the engine cadence). *Expected: stops a **pinned CPU core / pinned Mali GPU while screen-locked** — the largest battery item in the audit.* (PERF-BATTERY-NETWORK-01)
5. **Add a thermal-aware 117HD governor** (PowerManager listener → live preset/swap-interval downgrade on MODERATE+). *Expected: converts the device-confirmed decay-to-SEVERE-in-~1–2 min into a sustainable fps floor.* (PERF-MEMORY-THERMAL-01)
6. **Short-circuit `updateChrome()` on an unchanged snapshot** (mirror `updateWorldMap`'s `if (snap == last) return`), folding in the `railsShown`/`mapOpen`/login-window inputs. *Expected: removes a per-frame `JSONObject` parse + ~3 IntArray allocs on every static frame → lower UI-thread GC cadence.* (PERF-FRAME-PACING-01 = PERF-COMPOSE-UI-01 = PERF-MEMORY-THERMAL-03)

## 3. Detailed entries (by area)

### Area A — Cold-start (the ~30 s unpack headline)

#### PERF-COLD-START-01 — 8 KB single-thread unpack of 198 MB incl. unbooted jars *(CONFIRM, ~5–10 s + −30.6 MB, S, low, P1)*
- **Mechanism:** `AssetInstaller.copyAssetDir` (`AssetInstaller.kt:51-65`) is a single-threaded recursive walk on the jvm-boot thread (`MainActivity.kt:912 → bootJvm:2565 → ensureInstalled`); the leaf copy at `:57` is `input.copyTo(it)` with **no `bufferSize`** → Kotlin `DEFAULT_BUFFER_SIZE = 8192`. The 110.8 MB `lib/modules` single file is copied in ~13,500 8 KB read/write syscalls. It copies the **whole** tree unconditionally, including `client-*-shaded.jar` (30,796,676 B), `gpu-smoke.jar` (26,472 B), `hello.jar` (1,526 B) — **none on the Android boot classpath** (`MainActivity.kt:2618` = `[gpu:rlhd:probes]`; jar-resolution at `:2603` globs only those).
- **Measure (inspection; sec=device):** wrap `ensureInstalled` in `System.nanoTime()` + per-file ms for files >1 MB; `adb shell pm clear dev.audaro.helloshell`, launch, read logcat. Independently `adb shell 'ls -la /data/data/dev.audaro.helloshell/files/jvm'` to confirm the 3 unbooted jars are present in `filesDir`. Bump buffer to 1 MB + exclude the 3 jars, re-clear, re-time for the delta.
- **Fix:** (1) `ByteArray(1 shl 20)` and `copyTo(out, 1 shl 20)` — fewer syscalls on the 110 MB file is the cheap win. (2) Filter `client-*-shaded.jar`/`gpu-smoke.jar`/`hello.jar` out of the unpack (or drop them from the Android asset set per SLM-JAR-01/SLM-JAR-05) → −30.6 MB copy outright. Parallelizing top-level children is secondary (the modules file dominates).
- **Impact:** several-fold large-file throughput (syscall-bound → bulk IO); excluding the 3 jars removes ~15.5% of the copy; plausibly **~5–10 s** off the ~30 s unpack; **−30.6 MB** `filesDir`.
- **Scope:** android-only. **Tag:** inspection (bytes + code path measured; second-count needs-device). **Verification:** mechanism + on-disk sizes confirmed; buffer provably 8 KB; both fix levers safe (excluded files not on the boot classpath).

#### PERF-COLD-START-06 — incremental re-unpack (split JRE-BASE from jars-tag) *(CONFIRM, ~30 s → few s per jar bump, M, low, P2)*
- **Mechanism:** `ensureInstalled` compares one coarse marker `v5-<runtime.tag>` vs `.installed-tag`; on any mismatch `root.deleteRecursively()` + full recopy of all 198 MB (`AssetInstaller.kt:31-39`). `runtime.tag = sha256(shaded + probes + gpu + rlhd)` (`stage-mobile-runtime.sh`), so a one-byte gpu.jar change (the common dev iteration) bumps the tag and re-unpacks the **byte-identical 132 MB JRE**. BASE/tag split only decides *whether*, not *what*.
- **Measure (inspection):** rerun `stage-android-gpu-jar.sh → stage-mobile-runtime.sh`, reinstall, time `ensureInstalled` via the COLD-START-01 nanoTime logging; confirm full ~30 s recopy despite identical JRE.
- **Fix:** split into `ensureJre()` gated on BASE + `ensureJars()` gated on the tag (copies only `client-*`/`probes` jars), OR a per-file `path→size+sha` manifest skip. A jar-only bump then recopies ~38 MB. **Retain the wipe-on-change anti-staleness guarantee per-subtree** so old/new jars can't mix.
- **Impact:** the common jar-only update/redeploy avoids the 132 MB JRE recopy → ~30 s → a few seconds. First-ever install unchanged.
- **Scope:** android-only. **Tag:** inspection (saved-seconds needs-device). **Verification:** confirmed in `AssetInstaller.kt:31-39` + `stage-mobile-runtime.sh`; install/dev-iteration churn, not a per-launch runtime cost.

#### PERF-COLD-START-04 — release diagnostics armed on every accelerated boot *(ADJUST P1→P2, inspection, S, low)*
- **Mechanism:** `MainActivity.kt:2667-2670` arms `headless.capture.dir/.interval=10/.preLoginMax=40` on **every** boot; `:2761-2762` arms `gpuframedump` on every GPU boot; `:2773-2777` arms `gpuframedump`+`fpsprobe` on every 117HD boot — none `BuildConfig.DEBUG`-gated (vs `setStdioRedirect(BuildConfig.DEBUG)` at `:2784`). gpuframedump → up to 8 in-world-warmup PNG encodes (`JavaBridge.java:442-478`, gated `frameSeq≥150`).
- **Measure (inspection):** cold-launch a release-style GPU/117HD build; `adb shell ls -la <ext>/routec-frames` for PNGs + timestamps vs first frame; `am profile`/simpleperf around the encodes; A/B first-interactive-frame with flags gated off.
- **Fix:** gate all three behind `BuildConfig.DEBUG` (capture as `DEBUG || census`). Consumer reads (JavaBridge/HeadlessCapture/Hooks) untouched; absent dir ⇒ HeadlessCapture inert.
- **Impact:** removes the 8 gpuframedump warmup PNG encodes + capture PNGs from the warmup window; **per-frame capture "bookkeeping" is one `AtomicInteger.incrementAndGet()` — effectively free**, not a frame-budget concern.
- **Scope:** **android-only** (the `-D` edit is in `bootJvm`; iOS does not arm gpuframedump in release — `JVMLauncher.m:1154-1167` — so it cannot regress). **Tag:** inspection. **Verification:** ADJUST — steady-state per-frame cost overstated and scope corrected to android-only; the gpuframedump warmup cost is real ⇒ P2.

#### PERF-COLD-START-03 — no `-Xms`; heap grows during the boot alloc spike *(CONFIRM, needs-device, S, low, P2)*
- **Mechanism:** `bootJvm` passes `-Xmx512m` (`MainActivity.kt:2664`) with **no `-Xms`** (grep = none). HotSpot starts at its default initial heap and grows on demand; cold boot + first scene-load (class metadata, cache/region decode, plugin graph, AWT/CACIO buffers) is the heaviest allocation burst, so heap-resize/commit + extra young-GC land in exactly the window being shortened.
- **Measure (needs-device):** add `-Xlog:gc*:file=<filesDir>/gc.log:time` to a debug boot; count young-GC + total pause ms from `JNI_CreateJavaVM` to first LOGGED_IN frame; A/B `-Xms256m` (and `-Xms512m`). Watch RSS via `dumpsys meminfo`.
- **Fix:** add `-Xms256m` (conservative pre-commit under the 512 MB cap); consider `-Xms512m` only if device RSS headroom allows. Sizing-only, no correctness impact.
- **Impact:** removes heap-resize/young-GC pauses during boot; tens–low-hundreds ms; smoother first-scene pacing. Lower-bound if HotSpot's default initial heap is already large relative to a 512 MB cap — hence needs-device.
- **Scope:** android-only. **Tag:** needs-device. **Verification:** mechanism verified; magnitude genuinely uncertain (ergonomics), honestly flagged.

#### PERF-COLD-START-02 — no AppCDS/base-CDS archive *(ADJUST P1→P2, needs-device, M, med)*
- **Mechanism:** the embedded JRE ships **no CDS** (`lib/server/` = `{libjsig.so, libjvm.so}` only; `find … *.jsa` empty). Boot opts (`MainActivity.kt:2649-2683`) carry no `-Xshare`/`-XX:SharedArchiveFile`, so default `-Xshare:auto` finds nothing and every `JNI_CreateJavaVM` class-loads + bytecode-verifies the JDK base set cold from the 110.8 MB jimage. The build pieces are present: `lib/classlist` (1517 entries) + `bin/java` (verified `ELF aarch64`, bionic). This is **not** the jlink blocker (no jmods needed for CDS).
- **Measure (needs-device):** Phase A feasibility — `run-as` then `files/jvm/jre/bin/java -Xshare:dump`; or a one-time on-device `-XX:ArchiveClassesAtExit=<filesDir>/app-cds.jsa` over the real classpath. Phase B win — pass `-XX:SharedArchiveFile=<path>` + `-Xshare:auto`, A/B `JNI_CreateJavaVM`→first LOGIN_SCREEN frame.
- **Fix:** generate the archive **on first device boot** (`-XX:ArchiveClassesAtExit`) or ship a pre-dumped arm64 archive keyed to the exact libjvm+classpath; add `-XX:SharedArchiveFile=<filesDir>/app-cds.jsa -Xshare:auto`. **Keep `:auto` not `:on`** so a stale archive falls back instead of aborting (`ignoreUnrecognized=JNI_FALSE` → a bad flag is fatal). Regenerate whenever JRE/jars change (fold into `runtime.tag`).
- **Impact:** base CDS elides JDK class-load+verify (a *minority* of a real-RuneLite cold boot dominated by engine/cache/scene work). Frame as **a few hundred ms to ~1 s on class-load**, not the generic 15–30% headline.
- **Scope:** android-only. **Tag:** needs-device. **Verification:** ADJUST — mechanism confirmed precisely (no `.jsa`, classlist=1517, bin/java arm64); 15–30% impact overstated for this VM; M effort + med risk (regen coupling, silent-disable on mismatch) ⇒ P2.

#### PERF-COLD-START-05 — first frame gated on a fixed 20-frame warmup + 120-frame cooldown *(CONFIRM, needs-device, S, med, P2)*
- **Mechanism:** autologin is engine-side (`HeadlessLogin.tick`, per `Hooks.draw`). It won't attempt the Play-Now/EULA click until `draws ≥ WARMUP_DRAWS=20` (`HeadlessLogin.java:80,363-366`); a missed click waits `COOLDOWN_DRAWS=120` before re-arm (`:81,459-462`), up to `MAX_ATTEMPTS=5` (`:82`). On a cold boot the first frames are slow (class-load + cache decode + the ~2 s 117HD shader recompile), so 20 "frames" can be multiple wall-clock seconds before the first click — and it's a frame counter, **not** a login-screen-painted signal.
- **Measure (needs-device):** logcat already prints `[headless-login] Play Now attempt N/5` with dims+timestamps — measure first-LOGIN_SCREEN-frame → first attempt → LOGGED_IN; correlate with `[fpsprobe]`. A/B `WARMUP_DRAWS=10` + a readiness trigger.
- **Fix:** the constants are **already `-D`-overridable** (`Integer.getInteger("runelite.headless.autologin.warmup/.cooldown/.maxAttempts")` at `:80-82`) → Android tunes purely from `MainActivity` opts with **zero shared-code edit**, neutralizing the iOS-impact risk. Better: fire on `loginIndex == WELCOME_LOGIN_INDEX` once the canvas is displayable — but firing before the welcome panel is painted risks a missed click ⇒ a 120-draw penalty (hence risk:med).
- **Impact:** cuts the 20-slow-frame pad (1–3 s on a cold GPU/117HD boot) and avoids a ~120-frame miss penalty, without touching coordinates.
- **Scope:** shared/iOS-impacting (default constants) — **drive via `-D` from Android to keep it android-only**. **Tag:** needs-device. **Verification:** mechanism fully verified; `-D`-overridable escape confirmed; readiness-trigger has a real missed-click downside.

### Area B — Frame-pacing / jank

#### PERF-FRAME-PACING-03 — gpuframedump in release: 8 PNG encodes in in-world warmup *(CONFIRM, inspection, S, low, P1)*
- **Mechanism:** `MainActivity.kt:2760-2762` (GPU) + `:2772-2774` (117HD) unconditionally append `-Drunelite.gpuframedump=true`+`.dir` — not DEBUG-gated. `JavaBridge.FRAME_DUMP` (`:280`) → `gpuPublish` (`:421-437`, GPU-readback path only, never CPU) → `maybeDumpFrame` (`:442-478`): from `frameSeq≥150`, ≥50 seq apart, up to 8×, on the render thread: `Arrays.copyOf(src,w*h)` + `new BufferedImage(TYPE_INT_RGB)` + `img.setRGB(full)` + `ImageIO.write(png)` to external storage.
- **Measure (inspection):** `adb logcat | grep gpuframedump` → 8 `[gpuframedump] wrote …` in the first ~30–60 s; `adb shell ls -la <ext>/routec-frames/`; dumpsys gfxinfo framestats across warmup for 8 spaced spikes; perfetto for `ImageIO.write` slices.

- **Impact:** removes 8 full-frame copies + 8 rasters + 8 PNG DEFLATE encodes + 8 external writes from every accelerated release boot's warmup; a measurable cluster of startup frame-time spikes, zero release value.
- **Scope:** shared consumer / android-only arming. **Tag:** inspection. **Verification:** every line verified incl. gpuPublish scoping (not CPU) + iOS-off parity; P1 upheld (user-perceptible first-30 s judder).

#### PERF-FRAME-PACING-05 — headless.capture armed every release boot *(CONFIRM, inspection, S, low, P2)*
- **Mechanism:** `MainActivity.kt:2667/2669/2670` arm `headless.capture.dir/.interval=10/.preLoginMax=40` on **every** boot (CPU/GPU/117HD), ungated. Non-empty dir → `HeadlessCapture.ENABLED` (`:84`); `onDraw` (`:113-133`) runs `drawCount.incrementAndGet()` + a null-graphics check + `n%INTERVAL` branch on **every** `Hooks.draw`; `capture()` (`:177-227`) writes `setRGB`+PNG every 10 draws until budgets fill (MAX_FRAMES=20 logged-in default + preLoginMax=40 → "~26"/tens of PNGs).
- **Measure (inspection):** `adb logcat | grep headless-capture`; `adb shell ls <filesDir>/…`; time-to-first-interactive (logcat `ANDROID_A6_UI_GREEN` / first frameSeq) flags-on vs off; dumpsys gfxinfo across login for spaced encode spikes.
- **Fix:** gate `capture.dir/.interval/.preLoginMax` (+ the SLM-DFLAG-04 `runSeconds/captureTargetFrames` sentinels) behind `DEBUG || census`. Absent dir → inert (`if(!ENABLED) return :115`). iOS already `#if-DEBUG`-gates (`JVMLauncher.m:1054-1056`).
- **Impact:** removes the per-draw atomic+branch (within noise) + up to ~26 startup PNG encodes that contend with the login/first-frame cold-start path (writes to internal filesDir, spaced every 10 draws — modest, broader blast radius than -03: all 3 renderers).
- **Scope:** shared consumer / android-only arming. **Tag:** inspection. **Verification:** CONFIRM; P1→P2 (per-draw atomic within noise; PNG contention real but modest). Bundle with -03/-04 as one DEBUG-gate.

#### PERF-FRAME-PACING-01 ≡ COMPOSE-UI-01 ≡ MEMORY-THERMAL-03 — `updateChrome` per-frame JSON parse *(ADJUST P1→P2 for FP-01; CU-01/MT-03 CONFIRM P2, inspection, S, low)*
- **Mechanism:** `doFrame` (`MainActivity.kt:1629-1713`) re-posts at display rate (`:1712`) and unconditionally calls `updateChrome()` (`:1709`), which does `JSONObject(chromeSnapshotPub())` **every frame** (`:1852-1853`) + `chatRect/invRect/reorderRect` IntArray/ArrayList allocs (`:1891-1915`). - **Mechanism:** after `eglInitialize` (`librlawt.cpp:280`) the only validation is the clip-control self-test (`:387`) + a log-only caps probe (`:828`). `rc_AWT_createGLContext` silently `return`s on EGL bring-up failure (`:799`) with **no Kotlin signal** → the embedded GpuPlugin/HdPlugin issue GL calls with no current context. `rc_make_caps` **hardcodes `OpenGL33=TRUE`** (`:1080`) + `glTexStorage3D=1` (`:1082`) unconditionally — which **defeats** GpuPlugin's own guard `if(!glCapabilities.OpenGL33) throw` (`GpuPlugin.java:317-320`). `fboOk` gates only clip-control (`:825`), not rendering. In release, `checkGLErrors()` is a no-op unless debug (`GpuPlugin.java:2084`) and GLES no-ops don't throw, so `startUp`'s try/catch (`:384-402`) doesn't fire for the no-context case — "succeeds", renders nothing, and only the **240 s/3-frame watchdog** (`MainActivity.kt:1021-1022`) reverts.
- **Measure (needs-device):** device matrix (current coverage = Mali-G710 + SwiftShader emulator only); instrument createGLContext to log `glGetString(VENDOR/RENDERER/VERSION)` + `glCheckFramebufferStatus`; boot GPU/117HD, screenshot via `mcp__harness__android_screenshot`, diff vs the Mali golden via `mcp__harness__image_diff` to catch silent corruption a frames-presented counter would mark "success"; force an ES2-only config to confirm the silent-black path.
- **Fix:** (1) on EGL bring-up failure set a native `gpuInitFailed` flag the watchdog reads immediately (don't wait 240 s); (2) probe the real ES version + required extensions and reflect honestly in `rc_make_caps` — **but keep `OpenGL33=TRUE` whenever the ES3 context actually came up**, else it regresses capable devices (set FALSE only on real absence); (3) if `fboOk==false`, signal failure (don't render into an incomplete FBO); shorten the watchdog success window.
- **Impact:** turns silent corruption / 240 s black screen on tail GPUs into a fast clean CPU fallback (public-release device-compat gate). Zero fps cost (validation runs once at context create).
- **Scope:** android-only (`librlawt.cpp`; iOS uses `routec_zone_jni.m`). **Tag:** needs-device. **Verification:** ADJUST P1→P2 — mechanism confirmed (hardcoded OpenGL33 defeats the abort guard; checkGLErrors is a release no-op ⇒ silent-black is real), but zero frame-budget cost + Pixel 7a passes today + default renderer is CPU (auto-GPU only promotes after a caps probe) ⇒ small blast radius today. Fix flagged: honest-caps must still report OpenGL33=TRUE on a real ES3 context.

#### PERF-RENDERER-ROBUSTNESS-02 — rc_AWT_destroy leaves GL-object statics stale *(ADJUST impact, inspection, S, low, P3)*
- **Mechanism:** `rc_AWT_destroy` (`librlawt.cpp:830-838`) resets only EGL display objects (sCtx/sSurf/sWinSurf/sWin), leaving `sFbo/sColorRbo/sDepthRbo/sFboW/sFboH/sWinGen/sClipReverseZ/sTQGen/sTQId` and the `sJbCls` global ref stale. On in-process re-init `rcBuildFbo` glDeletes the stale names (`:312-314`). Today `forceDisablePlugins` (`MainActivity.kt:2697`) prevents an in-session GPU↔HD swap and the restart paths are hard process exits, so this is latent.
- **Measure (inspection):** statically verified. To exercise: temporarily allow an in-session stop→start cycle and watch `dumpsys meminfo` EGL mtrack across cycles.
- **Fix:** in `rc_AWT_destroy`, reset all GL-object statics to sentinels + `DeleteGlobalRef(sJbCls)`+null it, so a subsequent createGLContext starts clean.
- **Impact (corrected):** **not** an EGL/FBO memory leak — `eglDestroyContext` (`:835`) reclaims the context's FBO/RBO/timer-query objects; the stale `glDelete` on re-init is a spec-defined **no-op** (unknown name silently ignored), **not UB**; `sWinSurf`/`sWinGen`/`sDpy` actually re-init correctly. The one real residual is the `sJbCls` `NewGlobalRef` (never deleted) — but `rc_jb_cache` reuses it (`:183-184`), so it's a single idempotent class ref held for process life. Net: **stale-handle hygiene**, not a leak.
- **Scope:** android-only. **Tag:** inspection. **Verification:** ADJUST impact wording (no GPU-memory leak; no UB); P3 — cheap defensive fix worth keeping for a future in-session switch.

#### PERF-BATTERY-NETWORK-01 — engine + render thread never throttle backgrounded *(CONFIRM, inspection, M, med, P1)*
- **Mechanism:** on background/screen-lock, `surfaceDestroyed → JvmLauncher.setSurface(null)` (`MainActivity.kt:734-735`) → `g_window=null` (`jvm_bootstrap.cpp:1452`). **CPU path:** the engine has already done the full CPU scene rasterization; the loop only skips the final blit (`:1151`) and still runs the per-tick JNI batch (`:996-1138`) + `usleep(16000)` at ~60 Hz. **GPU/117HD:** the JNI batch runs **before** the `g_directPresent` early-continue at `:1143`, and the GpuPlugin draw thread still draws the **entire scene into the FBO** and calls `rc_AWT_swapBuffers` every frame; `rcEnsureWindowSurface()` returns false (`librlawt.cpp:954`) so **only** `eglSwapBuffers` is skipped — all scene/shadow GPU work is wasted. There is **no foreground/visibility signal** (no onPause/onResume; onStop only flushConfig `:2436-2444`). A foregrounded-then-locked phone keeps a CPU core (CPU) or the Mali GPU (117HD) doing full per-frame work.
- **Measure (inspection; mA=device):** `dumpsys batterystats --reset`, foreground in-world, lock 10 min, `dumpsys batterystats | grep -A20 dev.audaro.helloshell` for CPU/foreground-cpu + est mAh; cross-check `/proc/<pid>/stat` utime before/after lock; for 117HD watch `RouteC_framesPresented` stall while the engine fps log keeps printing (proves wasted draw).

Scope the engine stand-down as android-only / behind a visibility contract so it **does not fight iOS PiP** (iOS deliberately keeps rendering).
- **Impact:** eliminates the dominant idle/background drain — CPU drops a pinned core; 117HD stops pinning the Mali GPU; order-of-magnitude background CPU/GPU reduction, est. tens of mA on the GPU path. Foreground unchanged.
- **Scope:** shared/iOS-impacting (gate android-only). **Tag:** inspection (mA needs-device). **Verification:** mechanism verified precisely (poll runs before the bg check; FBO draw before the present-skip); the single biggest battery item in the audit. One fix inaccuracy (setFpsTarget) noted — shell-side throttle is sound/race-free. P1 upheld.

#### PERF-BATTERY-NETWORK-02 — no foreground service / wakelock / keepScreenOn *(CONFIRM, inspection, M, med, P2)*

When it survives it carries finding-01's drain with **no foreground-service attribution** (cached process doing sustained CPU — the Play-policy red flag).

- **Impact:** OS-scheduled/attributable background battery; survivability across Doze/LMK; removes a Play-policy violation surface. No foreground perf change.
- **Scope:** android-only. **Tag:** inspection. **Verification:** confirmed against the manifest + lifecycle; a survivability/policy contract decision, not a hot-path defect ⇒ P2.

## 4. Cold-start deep-dive (the ~30 s unpack — the headline)

The first-launch (and every-jar-rebuild) stall is the largest single UX cost in this phase. It decomposes into three sequential phases, each independently improvable, **none requiring a new toolchain artifact**:

**(a) Asset unpack — the ~30 s slice (PERF-COLD-START-01 + -06).** `AssetInstaller.copyAssetDir` walks the 198 MB `assets/jvm` tree single-threaded on the jvm-boot thread, streaming each file through Kotlin's no-arg `copyTo` → an **8 KB** buffer. The 110.8 MB `lib/modules` jimage alone costs ~13,500 read/write syscall pairs; on a phone that copy is **syscall-bound, not bandwidth-bound**. Two orthogonal levers: a **1 MB buffer** (`copyTo(out, 1 shl 20)`) collapses the syscall count ~128×, and **excluding the 3 unbooted jars** (`shaded` 30.6 MB + `gpu-smoke` + `hello`, none on the `[gpu:rlhd:probes]` boot classpath) removes ~15.5% of the bytes outright and ~30.6 MB of `filesDir`. Separately, the **re-unpack granularity** (-06) is all-or-nothing: a single coarse `v5-<runtime.tag>` marker triggers a full `deleteRecursively()` + 198 MB recopy whenever the tag (which folds the gpu/rlhd/shaded/probes SHAs) changes — i.e. **every dev jar rebuild recopies the byte-identical 132 MB JRE**. Splitting `ensureJre()` (BASE-gated) from `ensureJars()` (tag-gated) turns the common jar-only redeploy into a ~38 MB copy. *Combined expected: ~5–10 s off the first install + ~30 s → a few seconds on every subsequent jar bump.* This is also where the **Phase-1 jlink/localedata trims compound** — a smaller JRE is both a smaller APK *and* a smaller unpack.

**(b) JVM warmup — class-load + verify (PERF-COLD-START-02 + -03).** Every `JNI_CreateJavaVM` class-loads + bytecode-verifies the JDK base set (and the RuneLite/Guice/plugin graph) cold from the jimage. **AppCDS is the highest-leverage lever available without a new JRE artifact** — and uniquely feasible here because, unlike the jlink trim (which is blocked on a jmods-bearing bionic JDK), a CDS dump needs **only `bin/java` + `lib/modules` + `lib/classlist`, all already in the bundle** (`bin/java` verified `ELF aarch64` bionic; classlist = 1517 entries; no `.jsa` ships). Generate `app-cds.jsa` on first device boot via `-XX:ArchiveClassesAtExit` over the real classpath, then boot with `-XX:SharedArchiveFile=… -Xshare:auto`. **Calibrated expectation:** base CDS elides only JDK class-load+verify — a *minority* of a real-RuneLite cold boot dominated by engine/cache/scene work — so frame the win as **a few hundred ms to ~1 s**, not the generic-JDK 15–30%. Keep `-Xshare:auto` (never `:on`) because `ignoreUnrecognized=JNI_FALSE` makes any flag fatal and a path/classpath mismatch silently disables the archive; **regenerate it whenever libjvm/classpath/jars change** (fold into `runtime.tag`). Pair with **`-Xms256m`** (-03): with no `-Xms` the heap grows lazily through the boot/scene-load allocation spike, scattering young-GC + heap-resize pauses across the exact window being shortened.

**(c) First-frame gate — autologin warmup (PERF-COLD-START-05).** Even after the VM is up, the first real frame waits a **fixed 20-engine-frame** warmup before the first Play-Now click and a **120-frame cooldown** on any miss — a frame counter decoupled from actual login-screen-painted readiness, so the slowest boot frames (incl. the ~2 s 117HD shader recompile) pad time-to-in-world by 1–3 s. The constants are already `-D`-overridable, so Android can shorten the warmup / make it readiness-driven (`loginIndex == WELCOME_LOGIN_INDEX`) **without touching shared code** (keeping iOS login timing untouched).

**Sequencing:** (a) is pure win, low risk, do first (buffer bump is a one-liner; the exclusion + incremental split are the bulk of the seconds). (b) AppCDS is the biggest warmup lever but M/med (regen coupling) — feasibility-dump on device first. (c) is `-D`-tunable polish. **Also fold in §3's COLD-START-04 / FRAME-PACING-03/05 DEBUG-gating** — the release-armed PNG diagnostics land squarely in the in-world warmup window the user is waiting through.
