## What this produces: the iOS JNI GL bridge spec

`facade/org/lwjgl/opengl/GLALL.java` is **generated by reflecting the real LWJGL 3.3.2 `GL45C`** (`gen/RouteCGen.java`),
so it carries the **correct GL enum values** and **real method signatures** — it is directly the surface the JNI
bridge must implement:

- **74 GL constants** with real values (e.g. `GL_FRAMEBUFFER = 36160`, `GL_TEXTURE_2D_ARRAY = 35866`).
- **85 GL methods** (189 overloads) the plugin calls. All but **5 are GLES 3.0 core, 1:1** (census in the B1pt2
  brief): `glClearDepth`→`glClearDepthf`, `glMapBuffer`→`glMapBufferRange`, `glMultiDrawArrays`→`glDrawArrays`
  loop, `glDebugMessageControl`→no-op, and **`glClipControl(GL_ZERO_TO_ONE)` + reverse-Z → a real depth/projection
  port** (resolved by the archive prior art below).
- **`GLCapabilities`** — the bridge must set exactly **5 fields** the plugin reads: `OpenGL33` (**must be true** or
  the plugin aborts, `GpuPlugin.java:317`), `OpenGL45` (false → skips `glClipControl`, see reverse-Z), and the
  function-pointer probes `glTexStorage3D` (true, core ES3), `glDebugMessageControl` (false), and
  `GL_EXT_texture_filter_anisotropic` (true on iOS).
- **`AWTContext`** offscreen analogue — 9 members; the iOS shim: `createGLContext()` makes an EAGL ES3 context
  current, `getFramebuffer(false)` returns OUR offscreen FBO as "framebuffer 0", `swapBuffers()` no-op (we
  `glReadPixels` into the `int[]` blit), `setSwapInterval`/`getBufferMode` trivial.
- Support: `GL.createCapabilities/getCapabilities`, `GLUtil.setupDebugMessageCallback`→null, `Callback`,
  `Configuration.SHARED_LIBRARY_EXTRACT_DIRECTORY`, `BufferUtils`, `EXTTextureFilterAnisotropic` (2 consts).

## Prior art reused (predecessor archive `/Users/jordanmm/runelite/ios-spike`, patterns only — GPL/own-repo)

The predecessor ran this same GpuPlugin→iOS-GLES port on miniJVM. Verified-transferable findings:

- **No compute in the base plugin** (re-confirmed on current source: zero `glDispatchCompute`/OpenCL; CPU sort via
  `FacePrioritySorter`) → fully reachable on GLES 3.0. `glMultiDrawArrays`→`glDrawArrays` loop is the only draw
  change (`PHASE27B-RENDERER-PORT-PLAN.md`).
- **JNI GL binding pattern**: mechanical auto-generated stubs (`org.mini.gl.GL` → `jni_gl.c` → glad/GLES) — exactly
  our bridge shape, proven prod-grade on iOS. Template to mirror (don't vendor).
- **Reverse-Z resolution** (answers our one render-decision): RuneLite uses `glClearDepth(0)` + `GL_GREATER`
  (verified `GpuPlugin.java:973/987`); the iOS way is **mathematical reversed-Z via the projection matrix
  (`Mat4`, near→clip.z=2n), no `glClipControl`**, with `GL_GEQUAL` better than `GL_GREATER` for coplanar ties.
- **Compositing**: alpha-blend the UI texture over the 3D scene (UI buffer is transparent in the 3D region under
  GPU mode) — informs the publish seam; no rect mask needed.
- **Caveat / reframe**: the predecessor *shelved* its GPU port because (a) its miniJVM **injected client** emitted
  only the player's 8×8 zone of `DrawCallbacks` (NOT a RuneLite limit — the **real gamepack renders the full scene
  faithfully on desktop**) and (b) miniJVM execution was the real bottleneck (we're on OpenJDK now). Neither
  applies to us → the archive **de-risks** Route C rather than warning against it.
